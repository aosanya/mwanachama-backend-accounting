| W15 | 🐞 **BUG — `Post` lets a caller reverse the same entry twice, silently drifting the ledger off zero-sum.** `LedgerRepository.Post` (`memory.go`) only checks that `ReversesEntryID` names an entry that exists (`if _, ok := r.entries[e.ReversesEntryID]; !ok`); it never checks whether some other entry has already reversed that same id. Demonstrated live: open holder/pool accounts, `Post` an original entry (pool→holder, 1000), `Post` a correcting reversal (holder→pool, 1000, `ReversesEntryID: original.ID`) — succeeds, `Balance(holder)` correctly reads `0`. `Post` a **second** entry with the identical `ReversesEntryID: original.ID` — also succeeds with `err == nil`, and `Balance(holder)` now reads **`-1000`**, not `0`. The ledger's own stated zero-sum/append-only-correction invariant (`ledger.go`'s doc comment: "a mistake is corrected by a new entry... never touched") is violated by ordinary, unprivileged use of the public API — no adversarial input needed, just calling `Post` twice. Also reachable through the HTTP surface: `routes/entry.go`'s `PostEntry` handler calls `repo.Post` directly with no additional guard, so the same double-reversal is possible over `POST /entries`. Defect location: `memory.go`'s `Post` (and, by the same interface contract, any future Postgres `LedgerRepository` implementation) — needs to refuse a `ReversesEntryID` that some existing entry already names in its own `ReversesEntryID`. Pinned by `conformance_test.go`'s `W15_PostDoesNotRefuseADoubleReversal` subtest (run against both `TestMemoryRepository` and, once it exists, a Postgres conformance run) — must go RED once the fix lands. | 📋 | — |

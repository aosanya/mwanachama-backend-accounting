| W23 | 🧭 **Decide whether a multi-line Journal belongs on top of the two-account Entry.** Today every `Entry` is exactly one pair — one account debited, one credited, same amount — which is why the zero-sum invariant is *structural*: no posting can change the sum of every balance, so there is nothing to enforce. Standard bookkeeping also has a **journal**: one document, N lines, debits summing to credits, which is how a payroll run or a multi-tax invoice is posted as one thing rather than as five unlinked pairs. Adding it means a `journal` object with `journal_line` children (`account_id`, `side`, `amount`) and a real balance check on write, replacing a guarantee that currently costs nothing. Filed 2026-09-28 at the owner's explicit request while the field vocabulary was being made standard ("yes — file it as a new row"); **not built**, and nothing in the stack needs N lines yet. If it is built, `Entry` most likely becomes a one-line-pair convenience over a Journal rather than a second concept beside it. | 📋 | Filed 2026-09-28. Net-new scope, deliberately outside W16–W22's conversion. Decide before anything reaches for it, because retrofitting the balance check onto an existing ledger is harder than declaring it up front. |
